# 单会话内「修改 / 清空上下文并重注入」：能不能、值不值

日期 2026-10-29 · 只研究、未改任何源码 · 信源 `deepseek-harness/` @ 子模块 pin `dsh-v0.2.1-rc.2` 与本仓库插件源码。

问题来自李：「能否做到修改 deepseek-harness 这个模块抑或是通过插件做到单会话修改上下文 / 清空上下文重注入」。

本文分两部分：**第一部分**回答「有哪几条路、各自代价」（产品判断）；**第二部分**是机制笔记（上下文由什么组成、谁有权改、校验规则在哪），给第一部分当证据附录。两部分由两个独立代理分别查证，关键点上有交叉核对。

## 摘要

1. **「清空」要拆成三件事，答案不同**：模型看到的历史**能**改（往 append-only 日志追加一条带 `surfaceOp: replace` 的事件）；学生屏幕上的对话**不能**改（替换副本是 model-only，聊天只渲染 append 来源的消息）；两边都清只有一条路——**开新会话**。
2. **system prompt 清不掉，也不需要清**：surface 节点 0 是 system prompt 的保护区，只能被「一条恰好只盖住节点 0 的 system 消息」重写；而它本来就每 step 重新 assemble（`agent-loop/src/agent.ts:272` → `:411-424`），所以**会话中途改 section 下一个 step 就生效**——「重新注入」这件事天然成立。
3. **只靠插件就能做**（路径 A2）：`session.append('compaction/prune', …)` 记影子价，再 append 一条覆盖 `[1, N]` 的替换，不需要压缩服务、不需要改 harness；模板是上游自己的 `compaction-tool-result-pruner`。硬约束：必须在 idle 期做（turn 中途做会把自己的 tool/result 变成孤儿，序列化直接抛），跨度必须工具配对，错了在 append 点当场抛。
4. **上游的正规入口是 `compaction` 服务**：`compactRegion(start, end, agent, signal)` 是唯一能精确点名区间的入口；`compactNow` 只能空闲期跑、且只折叠到保留窗口之外（不是清空）。**但我们四个预设都没装它**——web-app 把 host 平面的 `compaction-basic`/`command-compact` 设了 `disabled: true`，预设内部的隔离组我们没补 → 现在长会话撞上下文窗口会**硬失败**，没有压缩兜底。这是现存缺口，跟本问题无关也该补。
5. **改 harness 是最差的选择**：子模块按规矩一行不改，落地等于给 `@deepseek-ai/dsh-session`/`dsh-agent-loop` 打 npm patch 改安装后的 dist，每次升 pin 重打，且 `systemPromptUpdate` 在上游协议里只允许 `'in-history'`（只追加、不重写第 0 条）。提示词里写「忽略以上内容」则是自欺：token 一分不省、审计断裂。
6. **价值判断**：对引导模式，**换题该开新会话**（收尾把 `status: review` + `guideOutcome` 写回 bank），**跑题该把 whereStuck / affect / insight 落 bank 再新起**。清空会把线索一起扔掉，并制造「学生还能往上翻、模型看不见」的不一致。另外模型不该自己触发清空——与「模型不能自己切模式」同一类越权。

# 第一部分：取径与代价

日期 2026-10-29 · 只读研究（未改任何源码）· 信源 `deepseek-harness/` @ 子模块 pin `dsh-v0.2.1-rc.2` 与本仓库插件源码。

缩写：`H/` = `deepseek-harness/packages/`。

## ① 结论

1. **「把历史折叠成摘要」是正规 seam，不是黑魔法**：`H/compaction/compaction/src/index.ts:119` 的 `CompactionEngine` 就是它，另有面向人的 `/compact` 命令（`H/compaction/command-compact/src/index.ts:101-107`）。路径 A 技术上成立。
2. **但 ensure-ILE 的四个模式里现在没有这个 seam**：web-app bundle 把 host 平面的 `compaction-basic` / `command-compact` 都 `disabled: true`（`H/bundle/web-app/cordis.patch.yml:539-543`），真正跑的实例在**预设内部的隔离组**里（`H/bundle/web-app/presets/standard.patch.yml:66-82`）；我们四个预设只挂了自己那一个插件（`dsh-plugin-guide/cordis.patch.yml:12-13`、`dsh-plugin-work/cordis.patch.yml:11-12`、`dsh-plugin-setup/cordis.patch.yml:11-12`，hrl 同构）。→ **A 的第一步不是写工具，是先给每个预设补挂压缩引擎。**
3. **只靠插件能做到的是 A2（自己 append 一条 surface replace）**：`Session.append` 对 surface 事件收 `surfaceOp`（`H/core/session/src/index.ts:798-802`），替换语义由 `planSurfaceEvent` 校验（`H/core/session/src/surface.ts:510-547`）；「先写 `compaction/prune` 影子价、再 append 替换」这套模板上游自己就在用（`H/compaction/compaction-tool-result-pruner/src/index.ts:160-171`）。不需要压缩服务、不额外调模型、不改 harness。
4. **模型侧清空 ≠ 用户侧清空**：聊天记录只渲染 append 来源的 user 消息（`H/client/ui-chat/src/client/conversation-nodes/message.ts:67`），替换副本是 model-only（`H/core/session/src/surface.ts:80-85` 的注释写死）。学生屏幕上那段对话**不会消失**；只有带 `compact-checkpoint` 来源标记的替换才会渲染成一张卡（`H/client/ui-chat/src/client/conversation-nodes/command.ts:123`、`H/compaction/compaction/src/checkpoint.ts:19-25`）。
5. **`/compact` 不等于清空**：它保留最近一截尾巴（`retainRatio`/`retainTokens`，`H/compaction/compaction-basic/src/config.ts:125-127`、`:195-198`），并且 `system/message` 永不进被折叠区间（`H/compaction/compaction-basic/src/region.ts:110-111`）。要整段清空必须用 `compactRegion(start,end,...)` 指跨度，或用 A2 自己写替换。
6. **推荐**：A2 + 给四个预设各补一行压缩组，入口做成空闲期命令；路径 B（开新会话）作为「真正换题」的主路径保留，因为**只有 B 能同时清掉屏幕和模型两侧**。**不走 C，不用 D。**

## ② 四条路径对比

注：C 之所以等价于「patch dist」，见仓库规矩——`deepseek-harness/` 是 pinned 子模块禁止修改（AGENTS.md 顶层与 `deepseek-harness/AGENTS.md` 开头都写了）。上游自己也把 `systemPromptUpdate` 只许 `'in-history'`（`H/llm/llm/src/index.ts:805-811`、`H/llm/llm-deepseek/src/config.ts:172-174`），所以 C 想「重写第 0 条 system」在协议层也没有对应的写入模式，得连协议一起改。

## ③ 路径 A：seam 的完整签名

```ts
// H/compaction/compaction/src/index.ts:67-70
interface CompactionAgentContext {
  session: Session
  options: { provider?: string; model?: string }
}
// :77-86 —— compactNow 要的上下文，比上面多一个 runMaintenance
interface ManualCompactAgentContext extends CompactionAgentContext {
  runMaintenance<T>(task: (signal: AbortSignal) => Promise<T>): Promise<T>
}
// :136 —— 自动策略用（压力/溢出触发）
abstract compactIfNeeded(agent: CompactionAgentContext, trigger: 'pressure' | 'context-overflow', signal: AbortSignal): Promise<CompactionResult | null>
// :162 —— 空闲期人工压缩
abstract compactNow(agent: ManualCompactAgentContext, signal: AbortSignal, sourceCommandId?: CommandId): Promise<CompactionResult | null>
// :187 —— 指定跨度强制折叠（唯一能精确「从这到那全清」的入口）
abstract compactRegion(start: SessionSeq, end: SessionSeq, agent: CompactionAgentContext, signal?: AbortSignal): Promise<CompactionResult>
// :94-120 CompactionResult = { compactionId, sourceCommandId?, startSeq, summarySeq, endSeq, summary, shadowedRange{start,end}, shadowedSeqs[], shadowedTokenCount }
```

`agent` 从哪来：**命令回调**里是 `invocation.agent`（`H/compaction/command-compact/src/index.ts:67` 就是 `compactNow(invocation.agent, invocation.signal, invocation.commandId)`）；**工具回调**里是 `exec.agent?: Agent`（`H/core/tools/src/index.ts:340`，注释写明 the agent on whose behalf the call runs）。`Agent` 两边的形状都满足：`session` + `options`（`H/core/agent/src/runtime-types.ts:166`）+ `runMaintenance`（`H/core/agent-loop/src/agent.ts:183`）。

**compactNow 之后历史是「被替换成摘要」，不是「只标记」**：`CompactionEngine` 的类注释写明 `a successful run replaces the selected surface span with one summary node`（`:112-117`），落地协议是 `compaction/start` → `compaction/summary` →（紧邻一条 `user/message` 承接替换）→ `compaction/end`（`H/compaction/compaction/src/types.ts:24-33`、`:72`）。紧邻是契约：`compaction/summary` 的 `shadowedTokenCount` 就是替换的「影子价」，计量器靠它减免（`H/llm/token-meter/src/surface-projection.ts:68-75`）。

**`/compact` 在我们四个预设里默认不装**：host 平面那两行被 web-app 关掉了（`H/bundle/web-app/cordis.patch.yml:539-543`），而四个预设的 `plugins` 只有自己那一个插件（`dsh-plugin-guide/cordis.patch.yml:12-13` 等），没有 compression 组。upstream 只有 `standard`/`ptc`/`minimal`/`cordis` 四个预设自带（`H/bundle/web-app/presets/standard.patch.yml:66-82`）。**好消息**：`commands` 服务本身在 host 平面（`H/bundle/base/cordis.patch.yml:317-318`），没被 web-app 关，所以「注册一个命令」这一步不需要动预设。

顺带纠一个前提：**billion-context 的 compress 不走这个 seam**。它 `ctx.inject(['llm'])` + `ctx.on('llm/stream', …)` 在请求出口改写 options（本机安装：`~/.dsh/profiles/desktop/node_modules/billion-context/dist/agent/dsh-native.js`，非本仓库），既不碰 session 日志也不产生 surface 替换——那是「改请求不改历史」的另一条路，在 ensure-ILE 里等于绕过 model-visible ⟺ logged，不建议。

### A 的失败模式

- `compactNow` **只能空闲期跑**：它进的 `runMaintenance` 在 agent 有活跃工作时**同步抛**（`H/core/agent-loop/src/agent.ts:184`）；`/compact` 的 busy 分支就是这条（`H/compaction/command-compact/src/index.ts:26-30`）。→ 工具在 turn 中途调它会直接炸。
- 摘要要**额外调一次模型**（`compaction-basic` 把 `summarizeWithLlm` 接进引擎：`H/compaction/compaction-basic/src/index.ts:30`），钱和延迟都算在压缩那一刻；摘要烂了还有 `summary` 这个失败码（`ManualCompactionErrorCode`，`H/compaction/compaction/src/index.ts:35-41`）。
- `compactNow` 只折叠到保留窗口之外，**不是清空**（`H/compaction/compaction-basic/src/config.ts:195-198`）。要全清得 `compactRegion(1, 最后一个节点)`，而它会拒绝**不配对**的跨度（tool 调用与结果必须成对，边检查工具是 `toolPairingBalancedBefore/After`，`H/compaction/compaction/src/index.ts:18`、`:168-186`）；跨度算错就抛。

### A2 的失败模式（自己写替换）

- **节点 0 是 system prompt 的保护区**：覆盖节点 0 的替换必须本身是一条只压着节点 0 的 `system/message`，否则直接抛（`H/core/session/src/surface.ts:493-507`）。→ 「连 system 一起清掉」这件事在 surface 层就做不到；清空只能是「节点 1..N 全换成一条」，system 原样留着。
- **不能中途做**：工具在执行中 append 替换，会把自己的 `tool/result` 变成孤儿（后到的结果在 surface 上没有对应的调用），下一次序列化直接 `DeepSeek Messages tool calls need immediate results`（`H/llm/llm-deepseek/src/serialize.ts:140-142`）。→ 入口必须是 idle。
- **计量要靠影子价**：替换前紧邻一条 `compaction/prune`（含 `shadowedRange`/`shadowedSeqs`/`shadowedTokenCount`），否则 token 账目对不上（`H/llm/token-meter/src/surface-projection.ts:7`、`:68-75`；模板 `H/compaction/compaction-tool-result-pruner/src/index.ts:160-171`）。`compaction/prune` 是 session 认识的事件类型（`H/core/session/src/known-event-types.ts:32-35`），不需要压缩服务在场。
- **屏幕上什么都不变**（见结论 4）。如果想让李看出「模型已经清过了」，得自己加一条可见标记（伪造 `compact-checkpoint` 来源会被渲染成「已压缩」卡，但那是谎报：那张卡的文案属于上游 compaction，见 `H/client/ui-chat/src/client/conversation-nodes/command.ts:101-131`）。
- 替换**不删事件**，只 shadow（`H/core/session/src/surface.ts:80-93`）：日志照旧增长，session 文件不会变小。

## ④ 路径 B：开新会话 + 摘要当第一句

现成的三段式，本仓库已经在跑（bankmanager 的「接着做」）：

```ts
// dsh-plugin-bankmanager/src/client/index.ts
sessionId = await sessions.create({ agentPreset: preset })   // :114
uiWorkspace?.openSession(sessionId)                          // :119
conversation.input.requestDraftInitialization(binding, {     // :126-129
  prompt: resumeText(view), clearPreviousDraft: true })
```

- 这三样都是**客户端**能力（`ctx.get('sessions')` / `ctx.get('uiWorkspace')` / `ctx.get('conversation')`，`:101-102`、`:121`），一个纯 client 插件就能干，不需要 host 服务。
- 服务端对应的创建入口是 `ctx.sessionController`（`H/api/session-controller/src/index.ts:158` 注册的名字）、`createSession(request)`（`:278`），请求里有 `cwd` 与 `agentPreset`（`:61-67`）。**收不收首条消息：不收**（`ApiSessionCreateRequest` 没有消息字段，`:61-67`），所以「第一条 user 消息」只能由学生按回车发出，或者由插件在创建后 append——但后者会替学生说话。
- 幂等：客户端 `sessions.create` 收 `{workspaceId?, cwd?, sessionId?, agentPreset?}`、返回 `SessionId`、失败抛 `SessionCreateError`（`H/api/session-controller/src/client/sessions/service.ts:434-444`）；服务端复用条件是 `reusable(sessionId)` 且没见过 `turn/start`（`H/api/session-controller/src/agent.ts:61-73`、`:488`）。所以 id 可以自己定——**但现成做法没用这条路**，靠的是「先查列表 + localStorage 记号」（`dsh-plugin-bankmanager/src/client/index.ts:60-75`、`:105-109`）。

### B 的失败模式

- 会话越开越多：resume 列表是唯一入口，没有合并/归档机制（本仓库现在没有）。
- 草稿可能塞不进去（`dsh-plugin-bankmanager/src/client/index.ts:130` 的 catch 吞掉失败）→ 学生看到空输入框，不知道要接着做哪题。
- 摘要只活在输入框里：学生可以改、可以删、可以直接回车前先问别的——「重注入」没有确定性。要做到确定性，得让模型自己在开场读 bank/memory（本仓库现行做法就是零注入 + 让模型先 `bank_list`，代价是模型可能忘记读）。
- 屏幕清空了，但**模型的旧记忆并没有「失效」**：新会话读到的还是 memory + bank + 学生档案，本来是设计意图；如果李的期待是「彻底忘掉」，B 也不满足——那需要删数据，不在本报告范围。

## ⑤ 路径 C：改 harness 暴露 `resetHistory`

要动的地方（按现在代码量估算，非精确行数）：

1. `H/core/session/src/surface.ts` —— 现在的替换已经能表达「清空（节点 1..N）」，缺的只是**一个不依赖 compaction 事务的公开入口**；如果真要加，是给 `Session` 加一个方法 + 在 `SurfaceIntent` 上放行（估 20-40 行 + 单测）。
2. `H/core/agent-loop/src/agent.ts` —— 必须处理「reset 发生在 turn 中」的情况（现在的 `requestSurfaceGeneration`/`startsSeries` 逻辑已经覆盖一部分，`:416-421`）。
3. 客户端：想让屏幕也清，得在 conversation 节点里认一条新的「已重置」事件（`H/client/ui-chat/src/client/conversation-nodes/`，一个 Definition + 一个 renderer）。

但**这三步在 A2 里全都不需要**：A2 用的就是现成的 `append` + `surfaceOp` 契约。所以 C 的唯一增量是「把 A2 那件事变成官方 API」，而代价是**从此维护一个上游补丁**：

- 子模块一行不改的规矩（AGENTS.md）下，C 落地方式只能是给 `@deepseek-ai/dsh-session` 等包打 patch，改的是**安装后的 dist**（本仓库 `patches/` 里那批就是这种，且 `resolutions` 的选择器必须按 `标识@描述符` 精确匹配，写错会静默不生效——AGENTS.md 坑·上游与文档 4 已经踩过）。
- 上游是 pre-stable（`deepseek-harness/AGENTS.md` 开头：Public APIs are pre-stable; update every consumer），`SESSION_FORMAT_VERSION` 与事件契约都可能变；每升一次 pin 就要重打、重验。
- 上游的 per-file 100% 覆盖率门与 snapshot 门不覆盖我们的补丁，等于自己给自己开一片无门禁区。

→ **C 的收益是「代码好看」，代价是长期负债，明确不建议。**

## ⑥ 路径 D：纯提示词「忽略以上内容」

判断：**自欺，不用。** 三条硬理由：

1. **token 一分不省**：模型请求里还是那全部内容；唯一「省」的是李的心理感受。前缀缓存确实不破（见 ⑦），但那本来就是不破的——省不到钱。
2. **审计与回放断裂**：上游规矩是「model-visible ⟺ logged」（`deepseek-harness/AGENTS.md` Conventions），提示词里的「忽略」不在日志里，事后无法区分「模型真的没看见」和「模型看见了但按要求忽略」。
3. **它没有锚点**：模型忘记遵守时没有任何机制会失败——本仓库已经因为同类原因放弃过「让模型自己遵守流程」的做法（见 AGENTS.md「跨会话只靠 bank + memory，零注入」那条的取舍）。

## ⑦ 前缀缓存：中途换 system / 清空历史各意味着什么

先把协议钉死：

- **system 只有一种写入模式**：`systemPromptUpdate` 的合法值只有 `'in-history'`（`H/llm/llm/src/index.ts:805-811`；`H/llm/llm-deepseek/src/config.ts:172-174` 在 catalog 层就拒其它值）。flash 声明 `systemPromptUpdate: 'in-history'` + `toolUpdate: 'addition-only'`（`H/llm/llm-deepseek/src/models.ts:8-14`）；`deepseek-v4-pro` 两条都没声明（`models.ts:16-20`）。**不存在「重写第 0 条 system」的模式。**
- **请求里没有独立的 system 字段来源**：agent-loop 组请求时不传 system（`H/core/agent-loop/src/agent.ts:695-702` 只有 messages/tools/sessionId），system prompt 是 messages 里的**节点 0**；序列化时**第一条** system 消息进 wire 的 `system` 字段（`H/llm/llm-deepseek/src/serialize.ts:106-116`、`:151`）。
- **中途换 system = 追加一条 in-band system 消息**，位置在前一条 user/tool-result 之后（`serialize.ts:85-89`、`:110-112`）。wire 的 `system` 字段不变 → **前缀缓存不破**（这正是 AGENTS.md 里「技术上可行但工具集换不了」那条的由来）。
- **清空历史 = 在节点 1..N 的位置上放一条替换**（`H/compaction/compaction/src/types.ts:26-33`；替换按 surface 位置而非 seq 区间，`H/core/session/src/surface.ts:415-435`）。wire 的 `system` 字段仍然不变（节点 0 静态），但**从第一个被 shadow 的节点开始，后续消息全部是新内容** → 缓存的有效前缀只剩「system 那一小段」，其余整条尾巴重新 prefill。一次清空 = 一次全量重算，但重算的东西很短，绝对成本低；之后每轮又能重新命中。
- **唯一会全失效的情形是「清空的同时换了 system 文本」**：surface 一变，`startsSeries` 被强制（`H/core/agent-loop/src/agent.ts:416-421`），`SystemPromptProjection.project()` 走合并分支——**文本不同就重写节点 0**（`H/core/agent-loop/src/runtime-context.ts:95-99`、`:105-110`）。节点 0 一改，wire 的 `system` 字段就变了，从第 0 个 token 起全部失效。文本相同则**不发事件**（`:98` 的 `head.text !== rendered` 判断），`system` 仍是原来那串字节。

一句话：**清空历史只丢后半段缓存；清空 + 换 prompt 才是全失效。** 我们四个模式的 prompt 是静态 md（`dsh-plugin-guide/src/index.ts:52-59` 的 `complete: true` 整份替换），所以 A2 的常见形态不会碰 system。

（DeepSeek 侧缓存的具体块粒度查不到：`H/` 里没有 provider 缓存实现，这是服务端行为。上面只用「前缀一致性」这个可核的事实。）

## ⑧ 对四个模式、尤其引导模式值不值

结论：**价值低，不建议为它单独造能力。** 理由分场景：

1. **「一道题讲完、要开新题」**——该开新会话，不是清空。收尾规矩要求把结果写回 bank（`status: review` + `guideOutcome`，schema 在 AGENTS.md 的 v2.1 段；字段实现在 `dsh-plugin-bankmanager/src/store.ts`），新题要靠 `bank_list` + `read_note` 重新定位。同会话清空会留下最坏的一种不一致：**学生往上翻还能看见那段对话，模型看不见**——学生会以为模型记得。
2. **「学生把话题带跑题、要重置」**——这是唯一真实场景，但正解不是清空，而是「把状态落到 bank 再新起会话」：schema 里已经有 `guide.sessions[].whereStuck` / `affect` / `effectiveHint` / `guide.insight` 这些字段，本来就是给「下一次的你」看的。清空会把这些线索一起扔掉，只剩一句摘要。
3. **「上下文装不下」**——高一的单题对话离窗口上限很远（`DEFAULT_CONTEXT_WINDOW` 具体值未核，见 ⑩），工程上没有动机；而且**我们四个预设连自动压缩都没挂**（见摘要第 4 条与第一部分 ① 第 2 条），所以现在这条压力根本不会被处理，只是也没人撞到过。

所以：**如果李的真实痛点是「模型开始乱扯、忘了自己是引导者」，那是提示词/守卫的问题，不是上下文长度的问题**；修上下文解决不了它，只会让模型连「这题走到哪」也一起忘掉。

真正可能值得做的最小版本：**不是清空，而是「把整道题的推演压成一条『这题到这儿了』的 checkpoint」**，即 A1 的默认形态（保留尾巴 + 一段摘要），用来把一节课的对话压到可控长度；入口给命令，不给工具。

## ⑨ 推荐与下一步（一天内可做完）

**推荐顺序：B 当主路径（换题），A2 当兜底（同一道题内治跑题 / 治长度），A1 只有当李明确要「摘要质量」时再上。C、D 不做。**

三个实验，按性价比排：

# 第二部分：机制笔记

日期 2026-10-29 · 只读研究（未改任何源码） · 信源：`deepseek-harness/` @ 子模块 pin `dsh-v0.2.1-rc.2`
上游路径前缀统一省略为 `packages/…`（= `deepseek-harness/packages/…`），`vendor/…` = `deepseek-harness/vendor/…`。

## ① 结论摘要

1. **一次请求里的 `messages` 只有一个来源**：session log 的 surface 视图（`session.deriveMessages()`）。没有第二个「消息池」，也没有可切换的「上下文变量」。
2. **改历史 = 往 append-only log 追加一条带 `surfaceOp:'replace'` 的事件**。这是通用机制而非 compaction 私有——`packages/core/session/src/types.ts:460-461` 的注释原文：`Used by compaction; any surface-replacing producer may use it.` 所以「单会话内改上下文」有正规地基。
3. **但有两个硬约束**：① 被遮蔽的每个 surface 节点都必须列进 `sourceEventSeqs`，否则 append 当场抛 `surface replace: sourceEventSeqs must include every shadowed surface node`（`surface.ts:363`）；② **surface 节点 0 是 system prompt，只能用一条 system/message 单独重写它**（`surface.ts:487-506`），不能把它卷进一条「替换整个历史」的 user 消息里。→ **「整体清空成一句短消息」在机制上不成立**，最接近的是从节点 1 开始遮蔽，节点 0 由 systemPrompt assemble 决定。
4. **system prompt 是另一条链，且每 step 重算**：`systemPrompt.assemble()`（`agent.ts:272`）→ 渲染 → `session.append('system/message', …)`（`agent.ts:416-424`）。所以**会话中途改 section 会在下一个 step 生效**（节点 0 被替换，或按路由的 `systemPromptUpdate:'in-history'` 追加一条新 system）。会话中途改不是「不生效」，而是「下一步才生效」。
5. **compaction 是现成的正规 seam，且接受外部指定区间**：服务名 `compaction`，`compactRegion(start, end, agent, signal)` 让你点名把 surface 上某段换成一条消息（`compaction/src/index.ts:168-192`）。它是「按需改一段历史」的可用入口。
6. **但 compaction 不等于清空**：摘要 token 必须小于被遮蔽区间原来的 route token（`compaction-basic/src/region.ts:418-421`），边界必须工具配对平衡（`region.ts:349-355`）。想「压成几乎没有」会被自己的判定拒绝。
7. **没有任何 truncate / rewind / rollback / 编辑某条历史 的 API**：`packages/core/session/src` 与 `packages/api/session-controller/src` 里 grep `truncate|rewind|rollback` 只有无关命中。会话层面唯一的重建手段是 **fork**：`sessions.fork(source, boundary)` 取 `events.slice(0, boundary+1)` 作种子（`session/src/fork.ts:21-30`，`session/src/index.ts:1380`）→ **boundary 之后全丢**，这是「等价回退/等价清空」的唯一官方途径。
8. **最干净的「清空并重新注入」其实是新开会话**：`session.create`（`api/session-controller/src/index.ts:300`）。预设切换、`recompose` 都**不碰历史**（`preset/agent-preset-registry/src/index.ts:334-339`：`mount` + emit，注释明说 "Rebind a blank Agent; the caller owns the blank-session check."）。
9. **第三方插件能拿到这些服务**：cordis 里 `inject` 声明服务名即可（`vendor/cordis/src/registry.ts:169-176`），`ctx.<name>` 未声明会抛 `cannot get property "X" without inject`（`vendor/cordis/src/reflect.ts:144`），`ctx.get(name)` 不需声明但可能 `undefined`（`reflect.ts:225-243`）。
10. **但 ensure-ILE 现在一个预设都没装 compaction**：`profiles/ensure-ile/package.json:6-17` 的 bundles 里 web-app 把 `compaction-basic`/`command-compact` 设成 `disabled: true`（`bundle/web-app/cordis.patch.yml:539-543`），而四个预设（setup/guide/work/hrl）都是**单插件** patch，没有 standard.patch.yml:66-82 那样的 `compaction` group。→ 学生会话里 `ctx.compaction` 不存在、`/compact` 命令不存在、自动压缩（`agent/pre-step` 与 `agent/request-error` 两个钩子）**完全没跑**。
11. **桌面壳没有相关 UI**：`dsh-plugin-desktop/src` 里 `compact` 全是侧边栏 compact rail，`reset` 只有整份数据目录的 factory reset，`fork` 只有 `utilityProcess.fork`。上游自带的分叉入口在客户端（看 ⑥ 的清单），桌面壳没接自己的版本。

- `ctx.inject([...names], cb)`：`ctx.plugin({inject, apply})` 的简写，等依赖就绪后才跑回调（`vendor/cordis/src/registry.ts:169-176` / `:300-301`）。

### 回到「能否在单个会话内改上下文 / 清空并重新注入」

| 想要的 | 机制上可行? | 怎么做 | 代价 |
| --- | --- | --- | --- |
| 会话中途改指令（system 段） | **可以** | 插件 `ctx.systemPrompt.section()` 注册的段落，下一次 `assemble` 就是新文本（`agent.ts:272` → `agent.ts:416-424`） | 只有下一 step 生效；`in-history` 路由是**追加**一条 system，节点 0 不动（`runtime-context.ts:95-102`） |
| 把某段历史换成一段摘要 | **可以** | 装 `compaction`（或自己 append 一条 `surfaceOp:{op:'replace'}` 的消息，带齐 `sourceEventSeqs`） | 摘要必须比原文小；边界要工具配对平衡；被遮蔽节点全要列进 `sourceEventSeqs` |
| 只丢掉后面一半历史（回退） | **可以，但要靠 fork** | `sessions.fork({ sessionId, atSeq })` → 新建子会话，`atSeq` 之后全丢（`session/src/fork.ts:21-30`） | 是新会话不是原会话；必须存在"已完成的 turn"才能作为边界（`session-controller/src/commands.ts:254` 的 `session/fork-unavailable`） |
| 就地清空整个会话再重新注入 | **不行** | ① append-only，没有删除事件；② 节点 0（system prompt）有保护区：只能由一条 `system/message` 单独重写（`surface.ts:487-506`）。→ 最接近的是「节点 1..N 全遮蔽 + 节点 0 由 systemPrompt 重写」，等于重造，不如新建会话 | 真要"清空"，新开会话（`session-controller/src/index.ts:300`）成本最低、语义最干净 |
