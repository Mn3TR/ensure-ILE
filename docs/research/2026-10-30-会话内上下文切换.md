# 会话内上下文切换：可行性与方案

> 2026-10-30。上一版研究 `docs/research/2026-10-29-单会话上下文重写.md` 的结论是「不建议改历史」——那是按「插件能用的手段」估的。
> 李补了关键前提：**要的是一个对话内的无缝切换，我们在做软件不是做插件**。按这个前提重查一遍代码，结论变了：**能做，而且不用改 `deepseek-harness/`**。
> 每条结论带 `文件:行号`；`H/` = `deepseek-harness/packages/`。

## 结论先说

- **能**：同一个会话、同一个 turn 之内，把模型看到的历史换成「新提示词 + 一段交接话」。学生不用开新会话，屏幕上的历史一条不少。
- **不用改 harness**：三个开关全在公开 seam 上——`agent/pre-step` 返回的 `PreStepDecision`、`session.append(type, data, { surfaceOp: { op: 'replace' } })`、`systemPrompt.section({ text: 函数 })`。
- **今天唯一的硬墙是「一个会话里不能换工具集」**（flash 的 `toolUpdate` 是 `addition-only`）。这道墙在我们这儿**恰好不存在**：guide / work / hrl 的工具集逐字相同（都只有 `read_note` 加 profile 根那批），只差提示词文本。**所以「会话内换模式」在 guide ↔ work ↔ hrl 之间是真能做的**——setup 例外（它注册的是 `setup_read` / `setup_update`）。
- **必须配一张自己的卡**：替换型 surface 事件在聊天界面上**完全不渲染**（`H/client/ui-chat/src/client/conversation-nodes/message.ts:67` 只吃 append 事件）。不画卡就是「模型已经忘了上文，学生屏幕上什么都没发生」——那是最坏的不无缝。

## 一、两条独立的源：模型看什么、学生看什么

| | 模型看到的 | 学生看到的 |
|---|---|---|
| 数据源 | `session.surface.nodes` → `session.deriveMessages()`（`H/core/agent-loop/src/agent.ts:688`） | 客户端按 `session/event` fold 出的 ConversationNode（`H/client/ui-chat/src/client/conversation-nodes/register.ts:22-38`） |
| 一条 `replace` 的影响 | 被遮蔽区间的节点消失，换成一个新节点 | **什么都不变**：替换事件不被任何正文 Definition 认领 |
| 往上翻还读得到原文吗 | 不需要（模型看不见了） | 读得到：「加载更早」(`ChatView.tsx:219-225`) 与轮次导航条 (`ChatView.tsx:199-206`) 都能回到任意一轮 |

这条分工是上游有意设计，原文写在 `H/core/session/src/surface.ts:78-93` 的 JSDoc 里：surface 会 shadow 被替换区间，所以它是 transcript 的错误来源——"a landed replacement would erase conversation the user already saw"。**「无缝」这件事上游已经替我们做完了**，我们要做的只是「在分叉那一行补一张卡」。

## 二、四个必须知道的机制事实

### 2.1 换提示词：`startsRequestSeries` 会让 system prompt 原地归一

`SystemPromptProjection.project()` 一个函数决定了一切（`H/core/agent-loop/src/runtime-context.ts:88-103`）：

```ts
const latest = nodes.findLast(node => node.text !== '') ?? head
if (!input.inHistory || input.startsSeries || rendered.length === 0) {
  // 归一：后面的 system 节点清空，head（node 0）原地替换成新文本
  const updates = nodes.slice(1).filter(n => n.text !== '').map(n => this.replace(n.seq, ''))
  if (head.text !== rendered) updates.push(this.replace(head.seq, rendered))
  return updates
}
if (latest.text === rendered) return [];   // 文本没变就一次都不写
return [{ message: createSystemMessage(rendered), intent: { surfaceOp: 'append' } }];  // 变了就追加
```

三个触发条件在 `H/core/agent-loop/src/agent.ts:415-421`：

```ts
startsSeries: startsRequestSeries
  || this.requestSurfaceGeneration !== this.session.surface.contentGeneration
  || (preparedCall?.toolUpdate === undefined && this.toolsChanged(assembly.tools))
```

**合起来给出三件事**：

1. 同一个提示词反复渲染，`latest.text === rendered` → **一次都不写**，不会每步堆一条 system 消息。
2. 提示词变了（`systemPromptUpdate: 'in-history'`）→ 追加一条新的 system 消息、不动 node 0，缓存前缀不破。
3. **只要我们做一次 `replace`（bump 了 `contentGeneration`），或者 pre-step 声明 `startsRequestSeries: true`，下一次请求就走「归一」**：node 0 被原地换成当前渲染出的文本，后面所有非空 system 节点被清空。

第 3 条就是「会话中途换提示词」的官方开关：换的是 `complete: true` 那一节的文本，下一次请求把 node 0 原地换掉，**不产生任何重复 token**。

### 2.2 什么时候动手是安全的

`agent/pre-step` 是 waterfall，每个 **step** 触发一次（不是每条用户消息一次）：

```ts
'agent/pre-step'(
  this: Scoped<Agent>,
  payload: { agent, messages: UserMessage[], turn, step, signal },
  next: () => Promise<PreStepDecision>,
): Promise<PreStepDecision>
// 签名 H/core/agent/src/runtime-types.ts:320
// 返回值 H/core/agent-loop/src/runtime-types.ts:111-119：{ kind: 'reject' } | { kind: 'enter', messages, startsRequestSeries?: true }
```

一个 turn 里的顺序（`H/core/agent-loop/src/agent.ts`）：

```
turn/start (:307) → preStep (:318) → step/start (:331) → 才 append decision.messages (:426-440)
  → assistant/message → tool/result (:282-289) → step/end → 下一个 pre-step
```

所以在 `step === 1` 的 pre-step 那一刻：

- **上一轮的 assistant 与全部 tool/result 都已提交**（工具是 await 完才回循环）→「上个 turn 的最后一条 surface 节点」是**平衡切点**（未答 tool call 数 = 0）；
- **本轮学生的新消息还没进 surface**（要等 step/start 之后才 append）→ 不会遮到自己。

这是唯一一个「学生刚说完、模型还没发请求」的窗口，也是 compaction-basic 自己在用的窗口（`H/compaction/compaction-basic/src/index.ts:158-176`：在 pre-step 里 await 压缩事务，然后照常 `return next()`）。

⚠️ **两条硬纪律**：

- **绝不在有 pending tool call 时动手**。`surface.ts` 完全不查 tool-call/result 配对（只有 seq 存在、两端更早、`sourceEventSeqs` 覆盖、node 0 保护四条），孤儿节点在本地静默通过；但下一次压缩时 `tool-pairing.ts:29-63` 判 `corrupt surface`，或者 provider 直接拒 dangling call（`H/core/session/src/repair.ts:164-166` 注释）。一旦坏了，这条会话之后每次压缩都抛，**永久坏**。
- **pre-step 里 `compactNow` 必失败**：它包在 `agent.runMaintenance()` 里，首行 `if (this.phase.kind !== 'idle') throw`（`agent.ts:184`），而 pre-step 时 phase 是 `running`（`agent.ts:269`）→ 统一转成 `ManualCompactionError('busy')`。要摘要只能用 `compactRegion`（它要求 open turn，pre-step 正合，`H/compaction/compaction-basic/src/region.ts:191-202`）。

### 2.3 一次 `replace` 的确切形状

compaction-basic 的写法可以直接照抄（`H/compaction/compaction-basic/src/region.ts:506-509`）：

```ts
session.append('user/message', createUserMessage({ content, source }), {
  surfaceOp: { op: 'replace', startSeq: start, endSeq: end },
  sourceEventSeqs: [startEvent.seq, summaryEvent.seq, ...shadowedSeqs],
});
```

`surfaceOp: 'replace'` 只有四条校验（`H/core/session/src/surface.ts:509-547` 的 `planSurfaceEvent`，依次）：

1. 两端必须**存在于当前 surface** 且 start ≤ end（`:414-435`，错误串 `surface replace: start seq N not found in surface`）；
2. 两端必须引用**更早**的事件（`:404-409`，`startSeq and endSeq must reference earlier events`）；
3. `sourceEventSeqs` 非空、无重复、全部更早，且**覆盖每一个被遮蔽的 surface 节点**（`:330-365`，`surface replace: sourceEventSeqs must include every shadowed surface node; missing ...`）；
4. **node 0 保护**：node 0 是 `system/message` 时，覆盖它的替换事件必须本身是 `system/message` 且只遮它一个（`:487-507`，`surface replace: node 0 holds the system prompt and may be rewritten only by a system/message over exactly that node`）。

第 4 条决定了我们的区间**从 node 1 开始**，node 0 留给 2.1 的「归一」去原地换——两件事分工，正好谁都不越界。

⛔ **不要冒用 `compact-checkpoint` 这个 source kind**：UI 会把它渲染成「已压缩」卡片，v3→v4 关系校验也要求它必须被 `compaction/start`…`compaction/end` 包住（`H/compaction/compaction/src/checkpoint.ts:33-50`、`H/client/ui-chat/src/client/conversation-nodes/message.ts:42`）。换题不是压缩，用普通 `user` source 就行。

### 2.4 学生屏幕上会发生什么

- **替换事件不渲染**：正文 Definition 只吃 append 事件（`message.ts:67`），替换型 `user/message` 只被 `command.ts` / `compaction.ts` 认领。所以**我们自己造的替换事件在界面上彻底消失**——学生屏上什么都没发生，而模型已经看不见前文。
- **必须自建一张卡**，三步全在我们自己的包里（范例就是 `dsh-plugin-bankmanager` 的 client 半边）：
  1. 声明合并加 kind：`declare module '@deepseek-ai/dsh-client-ui-chat/client' { interface ChatNodeDataMap { 'context-switch': MyData } }`（`ChatNodeDataMap` 是空壳，`H/client/ui-chat/src/client/contract/chat-nodes.ts:23-35`）；
  2. `ctx.uiConversation.events.register({ kind: 'context-switch', target: 'chat', match, start, update, buildViewNode })`（契约 `H/client/ui-conversation/src/client/contract/conversation.ts:213-273`；范例 `H/client/ui-user-questions/src/client/question-reply.ts:38-43,149-187`）；
  3. `ctx.slots.inject('conversation.chat.node', () => ctx.slots.register({ name: 'conversation.chat.node', key: 'context-switch', locale }, MyCard))`（slot 由 ui-chat 声明 `H/client/ui-chat/src/client/apply.ts:215-225`）。
- **落位**：卡的 `anchorSeq` 取那条替换事件的 seq，卡片就会正好落在「模型停止看见上文」的那一行——上游 compaction 自己就这么干（`H/client/ui-chat/src/client/conversation-nodes/compaction.ts:51-56`）。排序只看 `anchorSeq`（`chat-snapshot-builder.ts:522-535`），builder 对 kind 没有白名单（`:1110-1191`），所以新 kind 不需要上游同意。
- **文案必须写清**：「以上内容模型已经看不见了，往上翻仍可读」。不然学生只会看到「它突然忘了」，那比不切更糟。
- **滚动无风险**：遮蔽只在末尾新增一个节点、不删已渲染内容；「加载更早」(`ChatView.tsx:219-225`) 与轮次导航条 (`ChatView.tsx:199-206`，`turnOutline` 列全会话每一轮，点未加载的轮走 `loadThrough`) 都能翻回原文。

## 三、四级能力，做到哪一级

| 级别 | 做什么 | 谁看得到 | 成本 | 建议 |
|---|---|---|---|---|
| L1 换题不换提示词 | replace 掉 [node1..上个 turn 末]，换成一段交接话 | 模型丢上文，提示词不变 | 低（无模型调用） | 兜底，随时可做 |
| L2 换题 + 重注入提示词 | L1 + 换 `complete` 那一节的文本，靠「归一」原地换 node 0 | 同上 | 低 | 和 L1 一起做 |
| L3 会话内换模式 | L2，但文本换成另一个模式的 `prompts/*.md` | 引导学生 ↔ 独立做题 ↔ 答案优化 在一个会话里 | 低 | **推荐主路径**（工具集相同，这是唯一能这么做的三个模式） |
| L4 带摘要的切换 | L1 的交接话改由 `compactRegion` 生成（多调一次便宜模型） | 同上 | 中（一次 llm 调用 + 延迟） | 学生要求「别丢细节」时再开 |

## 四、推荐实现：`dsh-plugin-context`（新增，挂在 profile 根）

### 4.1 三块东西

1. **一个工具** `context_switch({ to, note })`：只**置一个待办标记**（`to` = guide / work / hrl / same，`note` = 交接话），不动历史。工具在 step 内被调用，真正的改写留到下一个 pre-step——那才是安全窗口。
2. **一个 pre-step 监听**：`step === 1` 且标记存在时，按 §2.3 的形状 append 一条 replace，覆盖 `[surface.nodes[1] .. 上一轮最后一条 surface 节点]`，然后 `return { ...next(), startsRequestSeries: true }`（或直接返回 `{ kind: 'enter', messages: payload.messages, startsRequestSeries: true }`）。
3. **一张卡**：§2.4 的三步，kind `context-switch`，文案带「切到<模式>」「上面那段模型已经看不见」「往上翻仍可读」。

### 4.2 提示词怎么跟着换

四个模式包现在是各自注册一节 `complete: true`、文本在 `apply()` 时 `readFileSync` 读完就固定了。改成「一节 + 动态文本」：

- 每个模式包仍读自己的 `prompts/*.md`，但注册时把文本包成 `text: ctx => { const mode = this.modeOf(ctx.agent); return render(mode) }`；`AssembleContext` 在装配时会带上 `agent`（`H/core/agent/src/runtime-types.ts:19-22` 的声明合并：`agent?: Agent`；`assembleContextFor()` 在 `H/core/agent/src/dispatch.ts:174-176` 填 `{ agent, scope: agent, signal? }`），所以**按会话取当前模式是合法的**。
- 当前模式存哪：写一条 **ignorable 的 log-only 会话事件**（`{ ignorable: true }` 的事件不会被 `KNOWN_SESSION_EVENT_TYPES` 拦，`surface.ts:304-313`），形如 `context/switch` `{ to, note, at }`。好处：重启/恢复会话时能从日志里读回当前模式，符合「模型可见 ⟺ 已记录」。
- **不要**用 memory 或 bank 存当前模式：那些是数据层，不是会话状态。

### 4.3 为什么不用现成的 `compactRegion`

能用，但三个不合口味：① 摘要必须比被遮内容小（`region.ts` 里 `framedSummaryTokenCount >= shadowedRouteTokenCount` 直接抛），交接话只有一两句时反而装不下；② 保留窗口按 token 政策算，不受我们控制；③ 卡片语义是「已压缩」，而学生刚做的事是「换了一道题」。

**但压缩引擎该装**：四个预设今天**都没装** `compaction-basic` / `command-compact`（web-app 把它们设成 `disabled: true`，见 `H/bundle/web-app/cordis.patch.yml:539-543`），所以长会话撞窗口是硬失败、`/compact` 也不存在。这跟本功能正交，但同一个 `agent/pre-step` 上有两个监听会互相打架，装上时要一起调。

## 五、代价与风险

| 项 | 结论 |
|---|---|
| token | 切换后请求里只剩下 node 0 + 一条交接话 + 新消息；被遮的历史不再计费 |
| 延迟 | L1–L3 零额外模型调用；L4 多一次（便宜模型） |
| 前缀缓存 | 换提示词必然让 system 段失效（node 0 文本变了）；历史段本来就清空了。**只有「换题但提示词一字不变」的 L1 能保住 system 段缓存** |
| 可回放 | 日志一条不删，被遮区间仍在 log 里；重放得到同一 surface。**前提是不写只有内存才有的状态** |
| 信息丢失 | 交接话是我们写的，细节会丢。补救：写回 `bank`（卡点 / insight / 下一步）再切，这样跨会话也能接 |
| 学生困惑 | 靠卡片文案；卡片不渲染成替换节点，所以不会出现「凭空多出一条假消息」 |
| 误触发 | 只在 `step === 1` 且标记存在时动手；工具只在学生真的要求切换时被调 |
| 与预设锁冲突 | `agentPreset` 元数据不变（还是 guide），换的只是提示词文本 —— 重启后要不要还原取决于日志里的 `context/switch` 事件 |

## 六、分步落地

1. **L1 + 卡片**（最小可用）：新包 `dsh-plugin-context`，一个工具 + 一个 pre-step 监听 + 一张卡。先只支持「同一模式内换题」，交接话由模型自己写进 `note`。
2. **L2/L3**：把四个模式包的 `complete` 节改成动态文本，`context_switch` 支持 `to: 'work' | 'hrl'`；`setup` 不参与（工具集不同）。
3. **L4**：接 `compactRegion` 做可选摘要（需要先给预设装上 `compaction-basic`）。
4. **收尾**：`guide.md` / `bank.md` 里写清「什么时候该切」，否则模型不会主动用这个工具。

## 七、没验证的

- 真机上「替换事件不渲染」这条只有代码推理，没实测（`message.ts:67` 的 `isAppendSurfaceEvent` 判据很硬，但没说 UI 一定不跳滚动位置）。
- `startsRequestSeries: true` 对 provider 侧缓存的具体影响（DeepSeek 的 prefix cache 是否会因为「新系列」全丢）——没查到代码层判据，需要真机对账。
- 自定义 ignorable 事件在 `session-format-v3-to-v4` 关系校验里是否被当成未知事件放过（`relationships.ts` 只校验已知类型，但没逐条读）。
- 一次 replace 之后 `requestSurfaceGeneration` 的归一是否会跟我们的区间打架（两边都动 system 节点，理论上 node 0 归归一、node1+ 归我们，未实测）。
- 卡片「展开被遮蔽区间」按钮：`shadowedRange` 有、`loadThrough(seq)` 能吃任意 seq，但滚动定位在 `ChatNavigation` 内部，第三方能不能优雅地「翻到并高亮」没验证。


## 八、落地记录（2026-10-30 晚，李 m01849「一次性做完」）

- **没有单独的 `dsh-plugin-context`**：这套机制并进了新的核包 `dsh-plugin-coreset`（唯一 complete 段 / `read_note` / cwd 遮蔽 / 模式注册表 / 工具 / pre-step / 投影全在一处）。理由是同一个 scope 只能有一条 complete 段，单开一个包还得再解决「谁持有段」的问题，不如让核长出手。
- **工具只置意图**：`context_switch({ to, summary })` 校验模式存在、`switchable`、摘要非空、不是当前模式，然后把 `{mode, summary}` 放进内存里的 pending，历史一个字不动。
- **落点在学生下一次开口的第一个 pre-step**（`step === 1`）：`session.append('user/message', notice, { surfaceOp: { op:'replace', startSeq: nodes[1], endSeq: nodes.at(-1) }, sourceEventSeqs })`，紧接着 append log-only 的 `ile/mode`（重启靠投影恢复当前模式）。node 0 不碰，system 由 runtime 用新模式的文本原地归一。`step !== 1` 一律放过——工具调用中途折历史会留下没有 result 的孤儿。
- **摘要是一封 user 消息，不进 system 段**：`source: { kind:'ile-handoff', form:'notice', summary }`、正文压到 120 字（`boundSummary`）。所以每次切换是「替换」不是「追加」，切多少次都不会滚雪球；学生屏幕上看不到它被渲染成「假消息」（它替换掉的正是被折掉的那一段）。
- **预设从四个并成两个加一个**：`work`（做题，起步 `guide`，挂 guide + work + hrl 三个人格）、`chat`、`setup`（`shouldRegisterSetup()` 为假就不注册）。换预设仍然等于开新会话，会话内换的只是人格文本，工具表不动（`addition-only`）。
- **客户端没做**：宿主侧 replace 之后界面自然只剩剩下的那点内容——这正是「交接完成后清空聊天记录」想要的效果，不需要 DOM 遮蔽。UI 侧查到的三条：`conversation.chat.node` 的 key 已被 ui-chat 声明，第三方接管会失去渲染授权（`ui-slots/src/index.ts:1245-1250` / `renderer.ts:278-286`）；fold 阶段没有过滤钩子（`chat-snapshot-builder.ts:522-535`）；卡片如果要加，官方家是 `conversation.chat.turnTail`（`ui-slots/src/slots.ts:435`）。
- **仍未验证**：折叠那一步会连着进两条 user 消息（交接话 + 学生这句），provider 组合没实测；上游 plan-mode 的 narration 是这个形状，但我们的 DeepSeek 通道要真机确认。不行就把交接话并进学生那条（pre-step 里学生消息已在手上）。
